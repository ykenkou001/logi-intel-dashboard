# CLO 業務ドメイン知識

**責任範囲**: CLO（物流統括管理者）の法的定義・業務内容・このプロジェクトとの関連。CLO 支援機能（フェーズ3）を実装する際の必読ドキュメント。

> ⚠️ **本プロジェクトの存在意義は CLO 支援に徹底的にコミットすることである**（[CLAUDE.md §1.5](../CLAUDE.md) 参照）。本ドキュメントは「何を作れば CLO に効くか」の判断基準そのもの。

---

## CLO とは

2026 年 4 月から、年間取扱貨物 **9 万トン以上** の特定荷主企業に選任義務化される「物流統括管理者」（Chief Logistics Officer）。

根拠法: 物資の流通の効率化に関する法律（改正物流効率化法）

---

## CLO の主要業務

1. **中長期計画の策定・提出**（初回 2026 年 10 月末）
2. **荷待ち・荷役時間の削減**
3. **積載率の向上**
4. **トラックドライバー負荷の低減**
5. **定期報告**（荷待ち・荷役時間）

---

## 罰則

| 違反内容 | 罰則 |
|--------|------|
| 未選任 | 100 万円以下の罰金 |
| 届出怠慢 | 20 万円以下の過料 |
| 計画未達 | 勧告・命令・企業名公表 |

## 国交省・経産省の公式テンプレート（重要）

CLO 支援アプリとしての本プロジェクトは、**以下の公式様式に準拠した出力を生成する**ことを目標とする。

### 計画書様式（必須準拠）

| 項目 | 内容 |
|------|------|
| 様式番号 | **様式第3別紙** 中長期計画書（特定荷主） |
| 形式 | Word（e-Gov 電子申請添付書類用、約 35KB） |
| 提出先 | 国土交通省（e-Gov 電子申請） |
| 提出期限 | **初年度: 2026 年 10 月末** / 以降: 毎年 7 月末 |
| 入手元 | [物流効率化法 理解促進ポータル](https://www.revised-logistics-act-portal.mlit.go.jp/planning/) / [経産省 物流効率化法ページ](https://www.meti.go.jp/policy/economy/distribution/butsuryu-kouritsuka.html) |

### 計画書の必須記載 3 項目（省令で規定）

各項目について「**実施措置**」「**計画内容**」「**実施時期**」を記載する。

1. **運転者一人当たりの一回の運送ごとの貨物の重量の増加に関する計画**（≒ 積載率向上）
2. **運転者の荷待ち時間の短縮に関する計画**
3. **運転者の荷役等時間の短縮に関する計画**

## フェーズ 3 実装設計

> **命名統一**: CLO 計画策定の文脈で使うツールはすべて `logi_clo_*` プレフィックスに統一する（旧表記 `logi_analyze_*` は廃止）。

### 1. 業界ベンチマーク分析（`logi_clo_benchmark_position`）

**何を計算するか**: 指定都道府県の業界規模を全国と比較してランク化する

**業種別分岐**:
- **運送業者向け**（H 運輸業，郵便業）: 既存 `logi_macro_overview` のロジックを再利用
- **荷主業種別**（製造業 D / 卸売業 I / 小売業 J）: 自社の JSIC 細分類コードに応じてベンチマーク対象を切替

| 指標 | 計算方法 | データソース |
|------|---------|------------|
| 全国ランク（1〜47位） | 47都道府県の事業所数を並べて順位付け | e-Stat 0004005642 × 47都道府県 |
| 全国シェア（%） | 当該都道府県 ÷ 全国合計 × 100 | 同上 |
| 隣接ブロック比較 | 同一地方ブロック内での順位（例: 関東6都県内） | 同上 |
| 物流効率指標 | 業種別物流原単位 × 自社売上 → 推計取扱量 vs 業界平均 | `core/static/industry_freight_coef.py` |

**実装上の注意**:
- e-Stat `getStatsData` を47回叩くと過剰アクセス → `cdArea` 未指定で全国一括取得して Python 側でフィルタ
- キャッシュキー: `benchmark:transport:v1`（TTL: 24時間）

---

### 2. ドライバー需給ギャップ推計（`logi_clo_driver_gap`）

**何を計算するか**: 2024年問題（960時間上限）による実質稼働力の減少幅を都道府県別に推計する

#### 計算式

```
需給ギャップ = 現在の実効稼働力 − 規制適用後の実効稼働力
            = ドライバー数 × (1 − 規制削減係数)
規制削減係数 ≈ 0.13〜0.14（業界団体推計: 年間残業960h上限で約13〜14%の実稼働時間減）
```

#### データソース

> **重要**: e-Stat の **`statsCode`**（省庁コード／統計分野ID）と **`statsDataId`**（個別統計表ID）は別物。`statsCode` は固定だが、`statsDataId` は調査年度ごとに新しく発行される。実装時は `getStatsList(statsCode=...)` で当年度の `statsDataId` を**動的取得**してキャッシュすること。

| データ | statsCode | 備考 |
|--------|-----------|------|
| 道路貨物運送業 就業者数（都道府県別）| `00200521`（国勢調査） | 職業: 輸送・機械運転従事者 大分類。statsDataId は `logi_estat_search` で都度特定 |
| ドライバー平均賃金（道路貨物運送業） | `00600310`（賃金構造基本統計） | 全国値のみで可。statsDataId は当年度版を動的取得 |

**探索が必要**: 国勢調査の statsDataId は `logi_estat_search` で「輸送 就業者 都道府県」を検索して特定する（実装前に要確認ステップあり）

### 3. 中長期計画ドラフト生成（`logi_clo_plan_draft`）

**何をするか**: FastMCP の `@mcp.tool()` として登録する統合ツール。フェーズ2.5 の出口層（`core/export/`）を呼び出して**ファイル成果物**を返す。

```
ツール内部の処理フロー:
1. logi_macro_overview(prefecture_name) → 外部環境データ収集
2. logi_clo_benchmark_position(company_profile) → 業界内ポジション把握
3. logi_clo_driver_gap(prefecture_name) → 2024年問題の影響試算
4. logi_clo_target_proposal(...) → 数値目標逆算
5. core/export/ppt_writer.py + docx_form3_writer.py + excel_writer.py
   → outputs/ にファイル一式を生成
6. {summary, files, citations} 構造でレスポンス返却
```

**計画書の構成（法定様式に準拠）**:
1. 表紙（会社名・対象期間）
2. **エグゼクティブサマリー**（経営層向け1枚要約・2枚目固定）
3. 外部環境分析（マクロ概況）
4. 自社ポジション（ベンチマーク）
5. ドライバー確保・育成計画（需給ギャップ対策）
6. 荷待ち・積載率改善目標（数値目標）
7. 施策一覧（実施措置・計画内容・実施時期）
8. 実行スケジュール（3〜5ヶ年）
9. 補助金・税制優遇（フェーズ3 Step6）
10. 出典一覧

**実装条件**: `logi_clo_benchmark_position` と `logi_clo_driver_gap` が完成してから着手する

---

### 4. 燃料価格動向分析（後回し）

**課題**: gogo.gs は「今日の価格」1点のみ。時系列分析には蓄積データが必要。

**方針**: 
- MCPサーバー起動のたびに価格履歴を SQLite の別テーブル `fuel_price_history` に自動追記する
- 数ヶ月蓄積後に傾向分析ツールを実装する
- 補助金データは経済産業省の補助金情報ページ（スクレイピング）を検討するが優先度低

**実装順序**: ベンチマーク・需給ギャップより後回し

## 出口設計（成果物フォーマット）

**Claude の会話画面に文字列を返すだけでは CLO 業務に届かない**。本アプリは以下のフォーマットでファイル成果物を出力する。

### 優先度

| 優先度 | 形式 | 用途 | 実装モジュール |
|------|------|------|------------|
| ★★★ 最優先 | **PPT** | 経営会議・取締役会の説明資料 | `core/export/ppt_writer.py` |
| ★★ 高 | **PDF** | 顧客提案・印刷配布 | `core/export/pdf_writer.py`（PPT → PDF 変換でも可） |
| ★★ 高 | **Excel** | 数値表・社内 BI への取込 | `core/export/excel_writer.py` |
| ★ 中 | **Markdown** | Claude → 人間レビュー → Word 整形 | `core/export/markdown_writer.py` |
| ★ 中 | **Word（様式第3別紙）** | 国交省 e-Gov 提出用 | `core/export/docx_form3_writer.py`（公式テンプレート埋込） |

### PPT 出力の設計方針

- ライブラリ: `python-pptx`（外部依存なし、Office 不要）
- マスタスライド: 暫定の汎用テンプレ `core/templates/micware_master.pptx` を同梱（micware ブランドは後日差し替え）
- **標準スライド構成（CLO 計画書発表用 / フェーズ3.0 + 3.5 完成形）**:
  1. **表紙**（会社名・対象期間）
  2. **★ エグゼクティブサマリー（1 ページ）★** ← 取締役会必須・**`logi_clo_plan_draft` で必ず生成**
     - 投資額・効果額・回収期間
     - 規制リスク（不作為のコスト）
     - 競合ポジション
     - 推奨意思決定
  3. 外部環境分析（マクロ概況：人口・運送業規模）
  4. 業界ポジション（全国順位・地域順位・業界平均比）
  5. ドライバー需給ギャップ（2024年問題の影響）
  6. 数値目標（積載率・CO2・拘束時間）+ **達成可能性スコア**（3.5）
  7. **推奨施策ポートフォリオ**（3.5）— 施策ライブラリから選定 × 評価スコア
  8. **財務インパクト**（3.5）— 物流 KPI → P&L 翻訳
  9. **シナリオ分析**（3.5）— 燃料・運賃の感度分析
  10. 実行スケジュール（3ヶ年ガントチャート）
  11. 補助金・税制優遇
  12. 出典一覧（全数値の出典 URL）

### エグゼクティブサマリー 1 ページの位置づけ

経営層 (CEO/CFO) は詳細スライドを読まない前提で、**「投資・効果・リスク・推奨」を 1 ページに集約**。
`core/export/exec_summary.py`（フェーズ3.5）が独立ツールとしても呼べるが、**`plan_draft` では必ず PPT の 2 ページ目に挿入される**運用とする。

### Web 経由ダウンロードの方針

フェーズ4 で Web ダッシュボードを構築する際、以下のエンドポイントで成果物を配信する:

```
GET /api/v1/clo/plan/draft?company_profile=...&format=pptx
GET /api/v1/clo/plan/draft?company_profile=...&format=pdf
GET /api/v1/clo/plan/draft?company_profile=...&format=xlsx
GET /api/v1/clo/plan/draft?company_profile=...&format=docx (様式第3別紙)
```

非エンジニアの CLO 担当者が、ブラウザから入力 → ダウンロードだけで成果物を取得できるようにする。

### 出典明示のルール

全成果物（PPT スライド・Excel セル・Markdown 数値）は、**出典を脚注または別シートで必ず付与する**。`core/export/citation.py` で統一管理し、以下を含める:

- データソース名（例: 経済センサス‐活動調査 2021）
- statsDataId / 告示番号 / 省令番号
- 取得日時
- 公式 URL

経営会議で「この数字の出典は？」と聞かれて即答できる状態にすることが、CLO の説明責任を果たす最低条件。

## CLO 支援アプリとしての実装優先順位（指針）

判断に迷ったらこの順で考える:

1. **法令準拠** > データ豊富さ — 国交省様式に沿わないものは作らない
2. **意思決定支援** > 単なるデータ提供 — 「どの施策を選ぶべきか」まで踏み込む
3. **成果物出力** > 分析の高度化 — PPT が出ないなら分析を増やす意味がない
4. **業界平均比較** > 単独数値 — 比較の文脈なしには CLO は使えない
5. **出典明示** > 計算の精緻化 — 出典のない数字は経営会議で使えない
6. **既存テンプレート流用** > オリジナル設計 — 公式記載事例集の構造に倣う
7. **経営層翻訳** > 物流専門用語 — 必ず財務インパクトに翻訳する

## スコープ外（フェーズ3.5 まで・恒久的）

CLO 支援に集中するため、以下は**当面スコープ外**とする。フェーズ3.5 までは焦点を保つために安易に手を広げない。

| 項目 | 理由 |
|------|------|
| 運送事業者向け契約書テンプレート | 法務領域・micware の競合領域とも接近 |
| バース予約 SaaS の構築 | 運用ツールは既存 SaaS（Hacobu 等）と競合する領域 |
| TMS / WMS 機能 | 既存の物流 IT ベンダー領域 |
| 個別企業の IR / CSR スクレイピング | 法的リスク・データ品質低 |

**判断基準**: 「**CLO 個人の机に常駐し、彼/彼女の意思決定を支援するか**」が Yes なら範囲内。
「**運送会社・現場オペレーション・荷役作業の効率化**」は範囲外。

## 将来連携検討（フェーズ 4.5 以降）

「現状はスコープ外だが、将来 logi-intel-dashboard と統合する価値が高い」候補。フェーズ 3.5 完了後に設計検討する。

| 項目 | 連携方向 |
|------|---------|
| **取引先（運送事業者）連携機能** | 荷主 CLO の計画 → 運送事業者の運用への伝達。改善基準告示準拠チェックの API 公開等 |
| **配車最適化 AI（社内別プロジェクト）** | 配車AI の運用実績データを取り込んで「計画 vs 実績ギャップ」を可視化、施策効果シミュレーション精度を実データで向上 |

**連携設計の原則**:
- logi-intel-dashboard は**戦略レイヤ（計画・評価・報告）**を担当
- 配車AI / 運送事業者ツールは**運用レイヤ（日々の配車・実行）**を担当
- データインターフェースは MCP / REST で疎結合（マイクロサービス境界を保つ）

### 配車最適化 AI 連携 計画案（フェーズ4.5 以降のスコープ）

社内別プロジェクトで開発中の配車最適化 AI と統合し、「**計画 → 実行 → 計測 → 改善**」の年次サイクルを自動化する。短期（フェーズ4.5）の実装ターゲットは下記2案。

#### 案A: 計画 → 実行 一気通貫の PDCA

```
[Plan]   logi-intel: 計画書ドラフト・数値目標（積載率50%・モーダルシフト30%）
   ↓ 計画値を MCP/API で配車AI へ転送
[Do]     配車AI: 日々の配車を計画値に沿うよう最適化
   ↓ 実績データ（実積載率・運行距離・荷待ち時間）を logi-intel へ
[Check]  logi-intel: 計画 vs 実績ギャップを業界ベンチマークと比較
   ↓ 達成率分析・未達リスク特定
[Act]    logi-intel: 次年度計画書を実績ベースで自動更新（様式第5 ドラフトも自動化）
```

**実装方針**:
- 配車AI 側に `logi-intel-dashboard` MCP クライアントを組み込む
- 計画値（数値目標・施策一覧）の取得 + 実績の返却を MCP ツールで実装
- 様式第5（定期報告書）への実績転記は `logi_clo_periodic_report_draft`（フェーズ3.5 Step 7）と連動

#### 案B: シミュレーション精度の実データ化

現状の `core/analytics/simulator.py` は業界平均値で概算しているが、配車AI の自社実績で精緻化する。

| 指標 | 現状（業界平均） | 配車AI 連携後（自社実データ） |
|------|---------------|----------------------------|
| 積載率 | 38%（全国平均） | 自社の実積載率（例: 32%） |
| 運行距離 | 500km（想定） | 自社の実運行距離分布 |
| CO2 削減効果 | ±50% 誤差 | ±10% 精度 |

**価値**: シミュレーション結果が「業界一般論」から「**自社固有の意思決定根拠**」になる。経営会議で「机上の空論ではなく実データに基づく意思決定」と説明できる。

## 自社プロフィールデータ（CompanyProfile）

### フェーズ 3.0〜3.5: サンプルデータで開発

本格的な自社データ取込基盤は**フェーズ 4.0 で実装**する。それまでは:

- `core/static/sample_company.py` に**架空の特定荷主企業データ**を定義
- 製造業・卸売業・連鎖化事業者の代表企業 3 社分を用意
- 開発・デモ・テストはこのサンプルデータで実施

### スキーマ（実装済み Pydantic v2）

```python
class CompanySite(BaseModel):
    """自社拠点。"""
    name: str                          # 拠点名（例: "東京物流センター"）
    site_type: Literal["factory", "dc", "store", "office", "warehouse"]
    prefecture: str                    # 都道府県名
    annual_freight_tons: float         # 年間取扱量（トン）

class CompanyProfile(BaseModel):
    """自社プロフィール（CLO 計画書ドラフト生成の入力）。"""
    company_id: str                    # 内部ID（ファイル名にも使用）
    name: str                          # 会社名
    jsic_code: str                     # 日本標準産業分類 細分類4桁（例: "3159"）
    main_business: str                 # 主たる事業（例: "電子部品製造業"）
    annual_revenue_jpy: int            # 年間売上（円）
    annual_freight_tons_total: float   # 年間取扱貨物量 合計（トン）— 9万トン判定用
    is_chain_franchise: bool           # 連鎖化事業者か（コンビニ本部等）
    fleet_count_owned: int             # 自社保有車両数
    fleet_count_outsourced: int        # 委託車両数（おおよそ）
    sites: list[CompanySite]           # 拠点リスト
    clo_name: str                      # CLO 役職・氏名
    plan_period_start_fy: int          # 計画期間 開始年度（例: 2026）
    plan_period_end_fy: int            # 計画期間 終了年度（例: 2030）
```

### サンプル3社の業種カバレッジ

- **製造業（電子部品）** JSIC 3159 — 特定第一種荷主（発荷主）想定
- **卸売業（インテリア）** JSIC 5514 — 特定第一種・第二種荷主（両方）想定
- **連鎖化事業者（コンビニ）** JSIC 5891 — 特定連鎖化事業者想定

各サンプルは `core/templates/clo_plan_examples/` の記載事例と整合させる。
