## 1. 背景

フェーズ 5.0 完了直前（PR #16 まで）の段階で、以下の 3 つの情報源を統合して、フェーズ 5.5 で着手すべきアップデートを再点検した。

| # | 情報源 | 提示する方向性 |
|---|---|---|
| 1 | `docs/notebooklm` 配下 4 文書（NotebookLM が示す「最高の CLO 支援アプリ」5 モジュール構成） | 機能拡充・網羅性の追求 |
| 2 | Web 調査 6 テーマ（改正物流効率化法・トラック適正化二法・適正原価・Scope3・フィジカルインターネット・物流 DX 事例） | 2026 年新規法令対応・標準化対応 |
| 3 | Codex 独立評価レポート（gpt-5.5） | 「広げず束ねろ」「継続運用と意思決定証跡が薄い」 |

## 2. 情報源の不一致と統合判断

3 情報源は **「フェーズ 5.5 で機能を広げるか、束ねるか」** で方向性が割れた。

| 情報源 | 主張 | Claude 評価 |
|---|---|---|
| NotebookLM | 5 モジュール網羅で「最高の CLO 支援アプリ」へ | 理想像として妥当だが、入れすぎると焦点がぼける |
| Web 調査 | Scope3 / 適正原価 / 多重下請 / フィジカルインターネットへの対応追加 | 重要だが提出期限（2026-10-31）後の Phase 6.0 で取り組むべき |
| Codex 独立評価 | 25+ ツールを Decision Support 一本線に再編集。継続運用と意思決定証跡を補強 | **筋論として最も鋭い。フェーズ 5.5 で採用** |

**結論**: フェーズ 5.5 は **Codex 案（束ね直し優先）** を採用。NotebookLM / Web 調査由来の新規機能はフェーズ 6.0 以降に整理する。これは CLAUDE.md §1.5 の「やらないこと」リストとも整合（「動いた」を完了とせず「CLO 計画書ドラフトに使える形で出た」を完了とする）。

## 4. アップデート案（Tier 別）

### 🔴 Tier S — フェーズ 5.5 で必達（Codex 勧告核心）

**主旨**: 単発デモから CLO の日常業務に接続。新機能ではなく既存 25+ ツールの束ね直し。

| # | 機能 | 中身 | 配置 | 工数感 |
|---|---|---|---|---|
| **S1** | **DecisionLog 永続化** | `today_decisions` の 3 判断 + `measure_eval` の Top3 + `scenario_sim` の baseline を「いつ・誰が・何を根拠に判断したか」で保存。様式第 5 定期報告の「経営判断の証跡」として再利用 | `core/io/decision_log_store.py`（新規） | 中 |
| **S2** | **KPI 時系列トラッキング** | 荷待ち時間・積載率・物流コスト比率を月次で履歴化。前回計画値との差分・悪化アラート。F2/J2 スコアの推移も | `core/io/measure_run_store.py` 拡張 / `/dashboard/cockpit` に時系列ペイン追加 | 中 |
| **S3** | **報告単位（Facility）管理レイヤ** | 定期報告で実務負荷になる「施設・測定期間・把握条件・除外理由」管理。`wait_heatmap` 出力を施設単位に紐付け | `core/io/facility_store.py`（新規） | 中 |
| **S4** | **罰則・社名公表リスクの経営層視覚化** | `submission_validator` の準拠率を「未対応時のリスク（行政指導→勧告→公表→100 万円罰金）」のステップフローで PPT に焼き付ける | `core/export/ppt_writer.py` 拡張 | 小 |
| **S5** | **25+ ツールの Decision Support 軸での再編集** | README / `/guide` を「対象判定 → 業界比較 → 施策評価 → 計画書 → 定期報告」の意思決定ストーリーで束ね直し。ツール一覧を機能別ではなく業務フロー別に並べる | `README.md` 全面改訂 / `docs/dashboard_feature_guide.md` 改訂 | 小 |

### 🟡 Tier A — フェーズ 6.0 初頭（2026-10 末提出後すぐ着手）

| # | 機能 | 法的根拠 | 中身 |
|---|---|---|---|
| **A1** | **Scope3 カテゴリ 4/9 算定モジュール** | 改正物流効率化法 + 省エネ法 2026-04 全面施行 | 既存 `core/static/co2_factors.py`（GHG プロトコル Ver.3.2）を使って `logi_clo_scope3_calculate` を追加。SBT 整合判定も |
| **A2** | **適正原価チェッカー** | トラック適正化二法（2025-06 公布・3 年以内施行） | 標準的運賃 2024-03 改定版（8% 引上 + 荷役対価加算）を `core/static/standard_freight.py` に取込済 → 自社支払い運賃が「適正原価」を下回らないか判定 |
| **A3** | **実運送体制管理簿支援** | 多重下請 2 回以内努力義務 | 3PL 利用荷主向け。委託先連鎖を構造化し、再委託回数を可視化 |

## 5. やらないことの再確認

- ❌ **フェーズ 5.5 で新 MCP ツールを追加しない** — 25+ ツールが「多すぎて伝わらない」状態の解消を先行
- ❌ **外部連携機能（共同配送マッチング / 3PL 議事）は当面入れない** — 焦点がぼけて差別化を失う
- ❌ **動態管理（GPS）連携は「取込口」までで、自前 IoT 実装はしない** — CLO の机上パートナーであって、テレマティクス SaaS ではない

## 7. 議論の経緯（Codex 勧告と Claude 判断の対応）

CLAUDE.md §9.4 に従って、Codex の指摘がどのように本計画に反映されたかを記録する。

| Codex 勧告 | Claude 判断 | 反映先 |
|---|---|---|
| 継続運用ログ／意思決定履歴が薄い | ◎ 採用 | Tier S1（DecisionLog 永続化） |
| KPI 実績の時系列トラッキングが弱い | ◎ 採用 | Tier S2 |
| 報告対象施設・測定条件の管理が見えない | ◎ 採用 | Tier S3 |
| 社内合意形成ワークフローを最小版で | △ 修正のうえ採用（Tier B3 のチケット管理に統合） | Tier B3 |
| 罰則・社名公表リスクの明示 | ◎ 採用 | Tier S4 |
| `certified_match` / `scenario_sim` は訴求が拡散しやすい | △ 観察のみ — 既存資産として残し、README 再編集で位置づけ整理 | Tier S5 |
| フェーズ 5.5 で新機能追加より既存機能の束ね直しを優先 | ◎ 全面採用 | 全体方針 |
| 外部連携除外の判断は妥当 | ◎ 採用 | スコープ宣言維持 |

加えて、Claude 単独判断として以下を追加:

- **Web 調査由来の Tier A（Scope3 / 適正原価 / 実運送体制管理簿）はフェーズ 6.0 で着手**
  - 理由: 2026-04 全面施行の Scope3 算定義務は 2026-10 末提出時点では「移行期」。Phase 5.5 で着手すると公開準備が拡散する
  - 反論可能性: 「2026-10 末の中長期計画作成時点で Scope3 算定が必要では？」 → 初回計画では Scope3 は「努力目標」レベルで足り、本格算定は翌年度報告から。Phase 6.0 着手で間に合う
